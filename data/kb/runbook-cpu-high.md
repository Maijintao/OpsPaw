# CPU 使用率过高告警处理方案

## 告警定义与触发条件

CPU 使用率过高的告警名为 HighCPUUsage,级别严重,触发条件是 CPU 使用率持续 5 分钟超过 80%(阈值 80%)。持续高 CPU 会导致应用响应变慢、请求超时增加、系统负载过高,严重时可能触发雪崩效应。查询 CPU 曲线用监控工具 query_cpu_metrics,传服务名和起止时间即可拿到时序数据与统计(avg/max/p95),返回里超过阈值会自动附带 alert_info 告警信息。

## CPU 过高的标准排查步骤

排查顺序:先用 query_cpu_metrics 看该服务最近 1 小时的 CPU 曲线,确认是否真的持续超 80%、是突增还是爬坡;再用 search_topic_by_service_name 按服务名找到日志主题拿 topic_id,配合 get_current_timestamp 构造时间窗,用 search_log 查应用日志里的 ERROR/WARN 记录;对照日志中的进程信息(PID、CPU 占比、启动时间)定位是哪个进程在烧 CPU。日志过滤条件示例:level:ERROR 或 message:超时。

## CPU 过高原因一:死循环或无限递归

特征:单个进程 CPU 占用接近 100%,应用日志中有大量重复的错误堆栈,内存使用也可能同步增长。处理:立即重启受影响的服务实例止血,然后查应用日志定位代码问题,必要时回滚到上一个稳定版本,最后通知开发团队修复代码缺陷。重启按变更管理规则执行:已宕机或单实例异常的重启属紧急止血,免审批。

## CPU 过高原因二:流量突增

特征:多个进程 CPU 使用率均匀升高,请求量明显增加,响应时间变长但无明显错误日志。处理:先确认是否有营销活动或突发流量,是正常业务增长就扩容实例分摊压力,怀疑恶意流量则启用限流策略,扩容后持续观察 CPU 是否回落。扩容属于变更操作,窗口内直接执行,窗口外需二线值班确认。

## CPU 过高原因三:定时任务重叠执行

特征:CPU 使用率呈周期性升高,特定时间点出现,日志中有定时任务执行记录。处理:检查定时任务配置,调整任务执行时间避免重叠,优化任务执行逻辑,给任务加互斥锁防止并发执行。这类属于配置调整,不需要紧急变更,走日常变更申请即可。

## CPU 过高原因四:数据库查询慢

特征:应用 CPU 高但业务逻辑简单,日志中有慢查询记录,数据库连接池占用高。处理:查慢 SQL 日志定位语句,优化 SQL 或加索引,检查是否有全表扫描,考虑增加缓存层减轻数据库压力。

## CPU 过高的紧急处置与时限要求

立即操作(5 分钟内):流量问题扩容、恶意流量限流、单实例异常重启。短期措施(30 分钟内):分析日志找根因,代码问题准备回滚,配置问题调整配置,持续监控 CPU 变化。恢复标准:CPU 降到 60% 以下,响应时间恢复正常,无新增错误日志,观察 30 分钟不复现。恢复进展按值班制度同步到值班群。

## CPU 过高相关告警与关联排查

CPU 过高常与以下告警关联出现:HighMemoryUsage(内存使用率过高,可能伴随频繁 GC 拉高 CPU)、HighLoadAverage(系统负载过高)、SlowResponse(响应时间过长)。排查时如果 CPU 和内存同步涨,优先按内存泄漏方向查;CPU 高但内存正常,优先查流量和慢查询。
