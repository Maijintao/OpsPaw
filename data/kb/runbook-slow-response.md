# 响应时间过长(SlowResponse)处理方案

## 告警定义与触发条件

响应时间过长的告警名为 SlowResponse,级别警告,触发条件是接口 P99 响应时间持续 10 分钟超过 2 秒。响应变慢通常先于宕机出现,是很多严重故障的前兆,不能拖到告警升级再处理。排查前先用 query_service 看服务状态,确认是「性能劣化」还是「运行中」,再看 CPU、内存水位是否异常。

## 响应过慢的标准排查步骤

排查顺序:先用监控工具 query_cpu_metrics 和 query_memory_metrics 看资源水位,排除资源瓶颈;再用 search_topic_by_service_name 找日志主题,用 search_log 查应用性能日志(过滤 message:超时 或 message:slow)和数据库慢查询日志(过滤 message:慢查询);对比告警时间点前后有什么变化(发布、配置变更、流量波动)。

## 响应过慢原因一:数据库慢查询

特征:应用日志中有慢 SQL 记录,数据库连接池占用高,接口耗时集中在数据库调用上。处理:用 EXPLAIN 分析慢 SQL 执行计划,优化语句或添加索引,检查是否有全表扫描,热点数据加缓存层。数据层问题不需要对应用服务做变更,走日常优化流程。

## 响应过慢原因二:外部 API 调用超时

特征:日志中有大量调用下游服务或第三方接口的超时记录,失败集中出现在同一依赖上。处理:给外部调用配置合理超时与重试,启用熔断防止被拖死,非关键依赖走降级返回缓存数据。如果下游服务自己挂了,通知对应团队处理,本服务做降级止血。

## 响应过慢原因三:代码性能问题与缓存失效

代码性能问题的特征:特定接口慢,日志无外部依赖异常,CPU 偏高。处理:性能分析定位热点函数,优化算法与循环,必要时扩容过渡。缓存失效或缓存穿透的特征:命中率骤降,数据库压力突增,响应同步变慢。处理:恢复缓存服务,对穿透请求加空值缓存或布隆过滤器,评估缓存过期策略是否合理。

## 响应过慢的紧急处置与验证

立即操作(5 分钟内):确认是否新发布引起,是则评估回滚;资源紧张就扩容。短期措施(30 分钟内):按排查结果处理根因,持续观察 P99 曲线。恢复标准:P99 降到 2 秒以下并稳定 30 分钟,错误率无抬升。处置进展按值班制度同步值班群。
